# 超星学习通题目解析与 AI 学习辅助工具：项目规划文档

> **文档版本：** v1.0\
> **规划日期：** 2026-10-25\
> **项目定位：** 个人学习与技术实践\
> **技术栈：** JavaScript、Chrome Extension Manifest V3、Spring Boot
> 3、Java、可选 MySQL\
> **第一版原则：** 先实现题目采集、AI
> 解题建议、答案校验与预览；保留人工确认，不自动提交作业，不绕过平台访问控制或反自动化机制。

------------------------------------------------------------------------

## 1. 项目概述

### 1.1 项目目标

构建一个浏览器端与后端分离的学习辅助系统：浏览器扩展在用户有权访问的练习页面中识别题目结构，将题目转换为统一
JSON；Spring Boot 后端负责数据校验、题目标准化、Prompt
构建、模型调用、结果解析与合法性校验；最终将答案建议和解释返回浏览器，按稳定标识匹配题目并供用户预览、确认。

### 1.2 第一版范围

**纳入范围**

-   Chrome 扩展程序（Manifest V3）及 Content Script。
-   单选题、多选题、填空题的基础识别。
-   统一题目 JSON 协议。
-   Spring Boot REST API。
-   可替换的大模型服务适配层。
-   结构化结果解析与答案合法性校验。
-   按 `pageId`、`questionId`、`optionId` 匹配结果。
-   答案建议、解释、错误状态的预览。
-   单元测试、接口测试、日志和基本安全控制。

**暂不纳入第一版**

-   自动提交作业或绕过平台限制。
-   复杂验证码、登录态提取或访问控制规避。
-   微服务、消息队列、Redis 等分布式基础设施。
-   强依赖平台内部接口或不稳定私有 API 的实现。
-   未经验证的自动化批量操作。

### 1.3 设计原则

1.  **职责分离：** 浏览器负责页面结构识别；后端负责业务编排与 AI 调用。
2.  **协议优先：** 前后端围绕版本化 DTO 协作，不互相依赖内部实现。
3.  **ID 驱动匹配：** 不按数组下标匹配答案。
4.  **默认不信任模型输出：** 每个模型响应都必须解析和校验。
5.  **失败可见：** 不确定、解析失败、过期结果应明确显示，不静默处理。
6.  **先小后大：** 先用模拟数据跑通全链路，再适配实际页面。
7.  **隐私最小化：** 只发送解题必需内容，不收集账号凭据、Cookie
    等敏感信息。

## 3. 端到端运行逻辑

### 3.1 主流程图

``` mermaid
flowchart TD
    A["用户打开允许测试的练习页面"] --> B["检测页面是否可识别"]
    B --> C{"题目容器是否存在且已加载？"}
    C -- "否" --> D["提示页面暂不支持或仍在加载"]
    C -- "是" --> E["DOM Adapter 采集题干、选项、填空控件"]
    E --> F["生成统一 JSON 与页面快照"]
    F --> G["用户检查采集结果"]
    G --> H["POST /api/v1/answers/solve"]
    H --> I["后端校验请求与标准化题目"]
    I --> J["构建 Prompt 并调用模型"]
    J --> K["解析模型响应"]
    K --> L["按原始题目映射并校验结果"]
    L --> M["返回答案建议、解释和逐题状态"]
    M --> N["前端校验 pageId、questionId、快照版本"]
    N --> O{"结果与当前页面匹配？"}
    O -- "否" --> P["标记结果过期，不应用"]
    O -- "是" --> Q["展示答案建议与解释"]
    Q --> R["用户逐题检查并确认"]
    R --> S["在支持的练习页面中进行受控的交互验证"]
    S --> T["显示成功、失败或需要人工处理的状态"]
```

### 3.2 浏览器端采集流程

1.  检查当前页面是否属于支持的页面类型。
2.  定位题目容器；如果容器未出现，提示用户稍后重试，而不是立即发送空数据。
3.  按题目容器逐题解析，避免将整个 `document.body.innerText`
    作为题目内容。
4.  识别题型、题干、选项、填空位置及必要的图片/公式信息。
5.  为当前批次生成 `pageId`、`questionId` 和快照版本。
6.  对采集结果执行本地结构校验。
7.  在扩展界面中展示采集结果，允许用户检查后再请求后端。

**动态页面注意事项**

-   如果题目由 JavaScript 异步渲染，可用 `MutationObserver`
    观察相关容器变化。
-   观察器应有明确的启动、停止和去重策略，避免页面持续变化时重复采集。
-   翻页或页面重新渲染后，应创建新快照并使旧结果失效。
-   对图片、公式、代码块和表格，不应假设纯文本足以表达全部题意。
-   选择器应集中放在 DOM Adapter 中，避免散落在业务代码各处。
-   选择器无法匹配时，应返回"页面结构不支持"，不应通过猜测生成题目。

### 3.3 后端处理流程

``` mermaid
flowchart TD
    A["QuestionBatchRequest"] --> B["Bean Validation / 请求大小限制"]
    B --> C["DTO 转换与题目标准化"]
    C --> D["题型与必填字段校验"]
    D --> E{"题目结构有效？"}
    E -- "否" --> F["返回逐题错误"]
    E -- "是" --> G["按上下文与题型组织模型请求"]
    G --> H["LlmClient：超时、限流、调用模型"]
    H --> I["解析 JSON / Schema"]
    I --> J{"模型输出有效？"}
    J -- "否" --> K["有限重试或标记失败"]
    J -- "是" --> L["按 questionId 关联原题"]
    L --> M["检查选项、答案数量与题型"]
    M --> N["AnswerBatchResponse"]
```

### 3.4 页面变化与过期结果

前端应为每次采集创建快照标识。收到后端结果后至少检查：

-   `pageId` 是否与当前页面批次一致。
-   `requestId` 是否属于当前请求。
-   `questionId` 是否存在于当前题目映射表。
-   题型与选项集合是否仍与快照一致。
-   当前页面是否已翻页或重新渲染。

任何一项不匹配，都应将结果标记为过期或无效，而不是尝试自动寻找"最相似"的题目。

### 4.3 Chrome 扩展通信方式

建议保持简单：

-   Content Script 负责与页面 DOM 交互。
-   Popup 负责用户操作和结果展示。
-   Background Service Worker
    只在需要跨组件协调、管理扩展消息或处理特定生命周期任务时使用。
-   不要为了"架构完整"而让所有数据都经过不必要的多次中转。

扩展应遵循 Manifest V3
权限最小化原则。只申请实际需要的页面访问权限，不收集 Cookie
或登录凭据。扩展与后端通信时，应通过明确配置的 API 地址和受控请求完成。

### 4.4 题型适配器设计

统一接口示意：

``` javascript
export class AnswerFiller {
  supports(question, result) {
    return false;
  }

  preview(question, result) {
    throw new Error("由具体题型适配器实现");
  }

  // 只有在用户明确确认、页面适配经过验证时才实现受控交互。
  async applyConfirmed(question, result) {
    throw new Error("尚未实现");
  }
}
```

每种题型独立实现，不要在一个大函数里堆积所有 DOM
操作。对不支持的控件，显示人工处理提示，而不是尝试猜测页面结构。

## 5. 题目数据协议设计

### 5.1 协议目标

-   前后端共享相同字段含义。
-   题型使用固定枚举。
-   每道题、每个选项、每个填空都可独立标识。
-   支持协议版本升级。
-   能表达题目不完整、模型不确定和逐题失败。

### 5.2 题目批次请求示例

``` json
{
  "schemaVersion": "1.0",
  "pageId": "page-session-001",
  "snapshotVersion": 1,
  "questions": [
    {
      "questionId": "q-001",
      "type": "SINGLE_CHOICE",
      "stem": "Java 中哪个关键字用于继承类？",
      "options": [
        {
          "optionId": "q-001-opt-a",
          "label": "A",
          "text": "implements"
        },
        {
          "optionId": "q-001-opt-b",
          "label": "B",
          "text": "extends"
        }
      ],
      "blanks": []
    },
    {
      "questionId": "q-002",
      "type": "FILL_BLANK",
      "stem": "Java 程序的入口方法是 ____。",
      "options": [],
      "blanks": [
        {
          "blankIndex": 0
        }
      ]
    }
  ]
}
```

以上为自定义示例协议，不代表目标网站的真实 DOM 或内部字段。

### 5.3 建议的数据字段

  字段                类型      说明
------------------- --------- --------------------------------------------------
  `schemaVersion`     string    协议版本
  `pageId`            string    当前采集批次/页面快照标识
  `snapshotVersion`   integer   同一页面内的快照版本
  `questionId`        string    当前批次内唯一的题目标识
  `type`              enum      `SINGLE_CHOICE`、`MULTIPLE_CHOICE`、`FILL_BLANK`
  `stem`              string    题干文本
  `options`           array     选项列表
  `optionId`          string    选项稳定标识
  `label`             string    选项展示标签，如 A、B、C
  `text`              string    选项文本
  `blanks`            array     填空位置列表
  `blankIndex`        integer   同一题内填空位置索引

**ID 设计要求**

-   `questionId` 不应仅由题干哈希构成，因为相同题干可能重复出现。
-   如果页面没有可靠的原始 ID，可在采集时生成 UUID，并将它与当前 DOM
    节点和快照绑定。
-   `optionId` 应来自采集阶段建立的选项映射，而不是让模型自由生成。
-   重新采集并发现结构变化时，应更新快照版本。
-   不要把 DOM 节点本身序列化发送给后端；只传输规范化后的数据。

### 5.4 答案结果协议示例

``` json
{
  "requestId": "req-20261025-001",
  "pageId": "page-session-001",
  "snapshotVersion": 1,
  "results": [
    {
      "questionId": "q-001",
      "type": "SINGLE_CHOICE",
      "status": "ANSWERED",
      "answer": {
        "optionIds": ["q-001-opt-b"],
        "blankAnswers": []
      },
      "explanation": "该选项符合题目所考查的继承关键字。",
      "confidence": null
    },
    {
      "questionId": "q-002",
      "type": "FILL_BLANK",
      "status": "UNCERTAIN",
      "answer": {
        "optionIds": [],
        "blankAnswers": []
      },
      "explanation": "当前题目上下文不足，需要进一步确认。",
      "confidence": null
    }
  ],
  "errors": []
}
```

`confidence`
可以为空。模型自报置信度不等于经过验证的真实正确率，因此第一版不应依赖这个数字来自动决定是否应用答案。

### 5.5 状态枚举

建议结果状态包括：

-   `ANSWERED`：已产生可解析的答案建议。
-   `UNCERTAIN`：题目有歧义、缺少上下文或模型无法判断。
-   `INVALID_INPUT`：采集数据不完整或不符合协议。
-   `FAILED`：模型调用或结果解析失败。
-   `STALE`：结果与当前页面快照不一致。

## 6. 答案匹配与校验设计

### 6.1 ID 驱动匹配流程

``` mermaid
flowchart TD
    A["收到 AnswerBatchResponse"] --> B["检查 requestId / pageId / snapshotVersion"]
    B --> C{"批次与快照匹配？"}
    C -- "否" --> X["标记 STALE，不应用"]
    C -- "是" --> D["通过 questionId 查找原题"]
    D --> E{"题目存在且唯一？"}
    E -- "否" --> Y["标记无效结果"]
    E -- "是" --> F["校验 type"]
    F --> G["校验 optionIds / blankAnswers"]
    G --> H{"字段与题型合法？"}
    H -- "否" --> Z["标记校验失败"]
    H -- "是" --> I["生成预览记录"]
    I --> J["等待用户检查与确认"]
```

### 6.2 必须执行的校验

-   `pageId`、`requestId` 与快照版本一致。
-   `questionId` 存在于当前题目映射中。
-   一个题目在响应中不能出现重复结果。
-   响应题型必须与原题一致。
-   单选题只能对应一个合法选项。
-   多选题选项必须存在且不能重复。
-   填空答案数量应与可识别的填空位置相匹配；若无法确定数量，应标记为需要人工检查。
-   不允许模型输出未出现在原题选项集合中的 `optionId`。
-   缺失题目、额外题目、无效字段应被明确记录。
-   不应在验证失败后自动使用"最相似题目"兜底。

### 6.3 为什么不能只依赖数组索引

假设采集顺序为 `q-001`、`q-002`、`q-003`，模型返回顺序却变成
`q-003`、`q-001`、`q-002`。只要使用 `questionId`
映射，顺序变化就不会导致错位。反之，依赖数组下标会把答案放到错误的题目上。

### 7.2 分层职责

  层                  职责               设计要求
------------------- ------------------ --------------------------------
  Controller          接口接入与响应     不写模型调用细节
  DTO                 请求和响应结构     使用明确类型与校验注解
  Service             编排业务流程       控制流程，不承载所有实现细节
  Parser              标准化、分类       可单元测试，不依赖网络
  Prompt              根据题型构建输入   模板可版本化，避免散落字符串
  AI Adapter          访问模型 API       隔离供应商差异，统一超时和异常
  Response Parser     解析模型输出       结构校验与错误分类
  Validator           业务合法性校验     不相信模型生成的标识
  Exception Handler   统一异常响应       不向客户端暴露密钥或堆栈

### 7.6 服务编排伪代码

``` java
public AnswerBatchResponse solve(QuestionBatchRequest request) {
    validateBatch(request);

    var normalized = questionService.normalize(request);
    var validQuestions = normalized.validQuestions();

    var promptGroups = promptService.groupByTypeAndContext(validQuestions);

    var modelResults = llmService.solve(promptGroups);

    var parsed = llmResponseParser.parse(modelResults);

    var validated = answerValidator.validateAgainstOriginalQuestions(
            normalized.originalMapping(),
            parsed
    );

    return responseFactory.build(request, validated);
}
```

这段伪代码展示职责划分，不是可直接编译的完整实现。建议让逐题失败可单独返回，避免一条坏数据导致整个批次无信息地失败。

## 8. 大模型与 Prompt 工程

### 8.1 抽象模型客户端

建议使用接口隔离模型供应商：

``` java
public interface LlmClient {
    LlmResponse generate(LlmRequest request);
}
```

具体实现负责：

-   API 地址和认证配置。
-   请求与响应格式转换。
-   超时和限流处理。
-   对供应商错误进行统一分类。
-   不在日志中输出密钥或不必要的题目个人信息。

模型密钥应保存在后端环境变量或安全配置中，不得写入扩展源码、Git
仓库或前端响应。

### 8.2 Prompt 构建原则

1.  系统提示词定义输出格式和一般要求。
2.  题目提示词提供题干、选项与必要上下文。
3.  单选、多选、填空使用不同的结构化输出约束。
4.  题干、网页文本和外部内容都应视为数据，而不是系统指令。
5.  遇到信息不足或歧义时，允许模型返回 `UNCERTAIN`。
6.  要求模型给出简短解释，方便用户检查。
7.  尽可能使用供应商支持的 JSON Schema / Structured Outputs。
8.  模型输出仍必须经过服务端校验。

### 8.3 推荐的模型输出内部结构

``` json
{
  "questionId": "q-001",
  "status": "ANSWERED",
  "selectedOptionLabels": ["B"],
  "blankAnswers": [],
  "explanation": "简短说明选择依据。"
}
```

建议让模型返回原题中的选项标签或序号，再由后端映射为原始
`optionId`。这样可以避免模型自由生成不存在的选项 ID。

### 8.4 批次策略

-   先按题型和题目上下文分组。
-   对依赖共同材料的题目保留必要上下文。
-   控制每批题目数量与 Token 长度。
-   对独立题目可有限并发，但需要并发上限。
-   对超时或限流采用有限重试和退避。
-   对解析失败的题目单独记录，不要无限重试。
-   记录模型名称、Prompt 版本、耗时、状态和测试结果，以便评估质量。

### 8.5 评估模型质量

不要把模型自报置信度当作正确率。准备一组可人工核对的测试题，按题型记录：

-   正确率。
-   结构化输出成功率。
-   不确定题目占比。
-   平均响应时间。
-   单题 Token 使用量或费用（如果供应商提供）。
-   不同 Prompt 版本的表现。

## 9. 异常处理与安全设计

### 9.1 异常清单

  异常              建议处理
----------------- ----------------------------------------
  页面未加载完成    提示稍后重试，不发送空批次
  DOM 结构不支持    返回明确的页面不支持状态
  题干或选项缺失    标记 `INVALID_INPUT`，不调用模型
  HTTP 请求失败     展示可理解的错误信息，允许有限重试
  模型超时或限流    记录错误类型，退避重试或返回 `FAILED`
  模型返回非 JSON   使用严格解析器处理；失败则标记，不猜测
  题目 ID 不存在    拒绝映射并记录校验错误
  结果顺序变化      按 ID 匹配，不依赖数组顺序
  页面发生变化      标记旧结果 `STALE`
  部分题目失败      返回成功结果与逐题错误，不隐瞒失败

### 9.2 安全要求

-   只采集解题所需的数据。
-   不采集、保存或上传 Cookie、账号密码、访问令牌。
-   不在浏览器脚本中暴露模型 API 密钥。
-   限制请求体大小、题目数量、字段长度和并发数。
-   配置允许的跨域来源；不要将 CORS 设置为无条件开放。
-   如果后端会被其他设备访问，应增加适当认证和速率限制。
-   日志不记录敏感凭据；必要时对题目内容进行脱敏或只记录摘要。
-   不将模型输出直接作为 HTML 渲染，避免注入风险。
-   对题目文本中的指令式内容保持数据与系统指令隔离。
-   尊重平台条款、课程规则和数据隐私要求；不绕过访问控制或反自动化机制。

## 16. 结论

建议将该项目实现为 **Chrome 扩展 + Spring Boot 模块化单体 +
可替换的大模型适配层**。

最核心的工程难点并不是单纯调用大模型，而是保证三个环节可靠：

1.  **采集可靠：** 从页面中正确识别题干、选项、填空和必要上下文。
2.  **解答可靠：**
    使用结构化输出、异常状态和服务端校验，避免把不确定结果当成确定答案。
3.  **映射可靠：** 通过 `pageId`、`questionId`、`optionId`
    与快照版本确保结果始终对应正确题目。

第一版应以"采集 → 解析 → 返回建议 → 校验 →
预览"为主线。等这些模块稳定后，再按实际需求增加历史记录、更多题型或异步处理能力。保持模块边界清晰、数据协议稳定、错误可见，才能让项目长期易维护、易扩展。
